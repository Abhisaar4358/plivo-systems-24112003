Flaky Network Transport

This submission implements a small real-time UDP transport for 160-byte frames generated every 20 ms[cite: 1]. Its goal is to deliver correct frames before their playout deadlines despite loss, random delay, duplication, and reordering, while keeping total relay traffic below twice the raw stream[cite: 1].

Architecture

harness source --47010--> sender --47001--> hostile relay --47002--> receiver --47020--> harness player
                                      ^                                  |
                                      +------ feedback ports reserved ----+

The sender and receiver are the only modified programs[cite: 1]. The Python harness and relay are not changed[cite: 1]. Feedback ports are reserved by the wire protocol but are unused in the current design because proactive recovery is more useful than a round-trip retransmission for short deadlines[cite: 1].

Wire format and protection

Every packet crossing the relay is 172 bytes: a 12-byte protocol header followed by a 160-byte body[cite: 1]. The header carries a magic byte, version, packet type, position in a block, big-endian base sequence number, and block size[cite: 1]. A data body is the original frame payload; a parity body is the bytewise XOR of the two data bodies in its block[cite: 1].

frame 2k       -- data packet -->
frame 2k + 1   -- data packet -->
frame 2k XOR frame 2k + 1 -- parity packet -->

If exactly one data packet is absent but parity and the other data packet arrive, the receiver recreates it with XOR and forwards the original required sequence + 160-byte payload harness format[cite: 1]. Received data is forwarded immediately; a bounded 16-block ring retains enough state to handle reordered packets and duplicates without unbounded memory growth.

Trade-offs

Sending one parity packet for every two data packets creates approximately 1.61x relay overhead, leaving room beneath the 2x limit[cite: 1]. It reduces the maximum wait for parity to one 20 ms frame interval and makes a single loss in a pair recoverable[cite: 1]. It cannot recover two unavailable packets in the same protected pair, so burst loss and low deadlines remain the primary limitations[cite: 1].

The system was successfully validated at a final playout delay of 100 ms across multiple random seeds for both Profile A and Profile B, consistently remaining comfortably beneath the 1.00% deadline miss cap and 2.0x bandwidth limit[cite: 1]. Lowering the playout delay further to 90 ms introduces deadline misses on Profile B because extreme delay spikes combined with the 20 ms parity frame window push total delivery time past the deadline[cite: 1].
